# Развёртывание ICT Help

Инструкция для установки системы на виртуалку с Ubuntu (22.04 / 24.04).

---

## Быстрая установка на чистую виртуалку

```bash
git clone https://github.com/fonsski/ict-oatk.git /tmp/ict-help
sudo bash /tmp/ict-help/deploy/install.sh
```

Скрипт сделает всё сам:

1. Поставит PHP 8.3, MySQL, nginx, Composer, Node.js
2. Развернёт проект в `/var/www/ict-help`
3. Создаст базу и пользователя БД со случайным паролем
4. Соберёт фронтенд, накатит миграции, заполнит справочники и инвентарь
5. Настроит nginx
6. **Включит автозапуск всех сервисов вместе с виртуалкой**

В конце скрипт покажет адрес системы и что осталось дописать в `.env`.

### После установки — обязательные шаги

Открыть `/var/www/ict-help/.env` и заполнить:

```ini
# Адрес, по которому система открывается
APP_URL=http://192.168.1.50

# Телефоны сотрудников — это логины для входа
STAFF_KHOROBROV_PHONE=+79001234567
STAFF_SINEGUBOV_PHONE=+79001234568
STAFF_GREBENSHCHIKOV_PHONE=+79001234569
STAFF_KUNGFU_PHONE=+79001234570
```

Затем **сначала** перечитать конфигурацию и **только потом** заводить учётки:

```bash
cd /var/www/ict-help
sudo -u www-data php artisan config:cache
sudo -u www-data php artisan db:seed --class=StaffUserSeeder --force
```

> Порядок важен. Пока конфигурация закэширована, Laravel не читает `.env`
> вовсе — сидер увидит пустые телефоны и напишет «не заведены», хотя номера
> в файле уже стоят. `config:cache` перечитывает `.env` и складывает новые
> значения в кэш.

Команда **один раз** покажет таблицу с паролями — сохраните её и раздайте
сотрудникам. Повторный запуск пароли не меняет.

Остаётся настроить почту — без неё нельзя восстановить забытый пароль:

```bash
sudo bash /var/www/ict-help/deploy/setup-mail.sh
```

## Почта

Настраивается до того, как кому-нибудь понадобится восстановить пароль:

```bash
sudo bash /var/www/ict-help/deploy/setup-mail.sh
```

Скрипт спросит, откуда отправлять письма, запишет всё в `.env` и сразу
проверит отправку — двумя письмами, прямым и через очередь.

| Вариант                    | Что нужно приготовить                        |
|----------------------------|----------------------------------------------|
| Google Workspace / Gmail   | пароль приложения (не пароль от ящика)       |
| Google Workspace, релей    | внешний IP сервера в консоли администратора  |
| Яндекс 360                 | пароль приложения, включённый доступ SMTP    |
| Mail.ru для бизнеса        | пароль для внешнего приложения               |
| Другой SMTP                | адрес сервера и порт, логин с паролем — если сервер их спрашивает |
| Сервер колледжа            | адрес релея — Postfix скрипт поставит сам    |

Ящик системы — `ict@oatk.org`.

### Google пишет «эта настройка недоступна для вашего аккаунта»

Так выглядит закрытая страница паролей приложений. Причина одна из двух:

- у ящика не включена двухэтапная проверка — без неё пароли приложений
  не выдаются вообще;
- администратор домена запретил их для организации.

Если включить двухэтапную проверку нельзя или запрет снимать не хотят,
пароль не нужен совсем — берите в скрипте **вариант 2**, ретранслятор.
Google Workspace пускает такие письма по внешнему IP-адресу сервера:
администратор заводит в консоли службу ретрансляции SMTP и вносит туда
адрес, с которого выходит виртуалка. Отправитель при этом должен быть в
домене организации.

Третий путь, если почта колледжа своя, — **вариант 6**: локальный Postfix
пересылает письма на внутренний почтовый сервер, тоже без пароля.

Пароль вводится вручную и на экране не показывается: в аргументах команды
его увидел бы любой через `ps`, и он остался бы в истории оболочки.
Прежний `.env` сохраняется рядом копией с отметкой времени.

### Почему одной прямой проверки мало

Письма системы — код восстановления пароля, уведомления по заявкам — уходят
через очередь. Рабочий процесс очереди читает конфигурацию один раз при
запуске, поэтому после правки `.env` он ещё какое-то время ходит на прежний
SMTP. Скрипт перезапускает `ict-help-queue` сам, но если правите `.env`
руками — перезапустите и его.

Проверить отправку в любой момент:

```bash
cd /var/www/ict-help
sudo -u www-data php artisan mail:test вы@oatk.org
sudo -u www-data php artisan mail:test вы@oatk.org --queued
```

Команда показывает текущие настройки (пароль — только фактом «задан»),
а при ошибке объясняет причину: не тот пароль, закрытый порт, неверное
шифрование, неразрешённый адрес отправителя.

### Чего делать нельзя

Не ставьте `MAIL_MAILER=log` на рабочем сервере. Этот драйвер не отправляет
письма, а пишет их в `storage/logs/laravel.log` целиком — вместе с кодом
восстановления пароля. Любой, кто читает журналы, получает возможность
сменить пароль кому угодно. `mail:test` такую настройку отвергает.

Если письма не приходят:

```bash
sudo -u www-data php artisan queue:failed
tail -50 /var/www/ict-help/storage/logs/queue.log
systemctl status ict-help-queue
```

## Автозапуск при включении виртуалки

Отдельно настраивается так (входит в `install.sh`, но можно запустить и одному):

```bash
sudo bash /var/www/ict-help/deploy/setup-autostart.sh
```

Включает автостарт для всего, из чего состоит система:

| Сервис                       | Назначение                          |
|------------------------------|-------------------------------------|
| `mysql`                      | база данных                         |
| `nginx`                      | веб-сервер                          |
| `php8.3-fpm`                 | обработчик PHP                      |
| `ict-help-queue.service`     | письма и уведомления из очереди     |
| `ict-help-reverb.service`    | WebSocket живых уведомлений         |
| `ict-help-scheduler.timer`   | периодические задачи (раз в минуту) |

После этого при перезагрузке виртуалки система поднимается сама.

Проверить состояние:

```bash
systemctl status ict-help-queue ict-help-reverb
systemctl list-timers ict-help-scheduler.timer
```

## Обновление системы

### С рабочей машины — одной командой

```bash
bash deploy/release.sh
```

Скрипт запускается из каталога проекта и делает выкат целиком: проверяет,
что нет незакоммиченного и что код уже в `origin`, показывает список
коммитов к выкату и спрашивает подтверждение, затем по SSH выполняет на
сервере `update.sh` и проверяет, что система поднялась — коммит доехал,
очередь и Reverb запущены, сайт отвечает 200.

Адрес сервера берётся из переменной окружения:

```bash
SERVER=sysadmin@192.168.0.170 bash deploy/release.sh
```

| Переменная   | По умолчанию                    |
|--------------|---------------------------------|
| `SERVER`     | `sysadmin@helpdesk.oatk.local`  |
| `APP_DIR`    | `/var/www/ict-help`             |
| `BRANCH`     | `main`                          |
| `HEALTH_URL` | берётся из `APP_URL` на сервере |

### Прямо на сервере

```bash
sudo bash /var/www/ict-help/deploy/update.sh
```

Скрипт снимет дамп базы (хранятся 10 последних в `storage/backups`),
включит режим обслуживания, заберёт новый код, накатит миграции,
пересоберёт кэш и перезапустит фоновые сервисы.

Если что-то пойдёт не так, сайт всё равно выйдет из режима обслуживания —
это гарантирует `trap` внутри скрипта.

### `detected dubious ownership` при получении кода

```
fatal: detected dubious ownership in repository at '/var/www/ict-help'
```

Каталог принадлежит `www-data`, а git внутри скрипта работает от root и
чужой репозиторий трогать отказывается. Свежие версии `update.sh` обходят
это сами, но обновиться до них старая версия уже не может — код ей как раз
и не даёт скачать эта ошибка. Разорвать круг разово:

```bash
sudo git config --global --add safe.directory /var/www/ict-help
```

Дальше `sudo bash deploy/update.sh` проходит как обычно, и повторять
команду не нужно.

## Что попадает в базу при первой установке

Боевой сидер (`ProductionSeeder`) заливает **только рабочие данные**:

- роли, категории оборудования, категории базы знаний, справочник ОС;
- реальный инвентарь колледжа: кабинеты и оборудование (`InventorySeeder`);
- учётные записи сотрудников отдела.

Демонстрационные данные — тестовые пользователи, показательные закупки,
FAQ главной — **в production не заливаются**. Они привязаны к проверке
окружения в `DatabaseSeeder` и работают только при `APP_ENV != production`.

### Состав отдела

|----------------------------------|--------------------------|----------------|

| Синегубов Вячеслав Александрович | Техник первой категории  | `technician`   |
| Гребенщиков Кирилл Дмитриевич    | Техник                   | `technician`   |

Список задаётся в `config/staff.php`, телефоны и пароли — через `.env`.

## Если после обновления посыпались ошибки 500

Чаще всего причина одна: код обновили вручную (`git pull` из-под своей
учётной записи), а не через `deploy/update.sh`. Новые файлы шаблонов
достаются владельцу, который их скачал, кэш скомпилированных представлений
не пересобран — и `www-data` не может дописать в `storage/`. Любая страница,
чей шаблон изменился, падает с 500.

Сначала посмотрите настоящую причину. На странице ошибки есть
«Идентификатор ошибки» — тот же номер лежит в журнале:

```bash
grep <идентификатор> /var/www/ict-help/storage/logs/laravel.log
```

Строка вида `Failed to open stream: Permission denied` подтверждает догадку.
Лечится так:

```bash
cd /var/www/ict-help
sudo chown -R www-data:www-data /var/www/ict-help
sudo chmod -R 775 storage bootstrap/cache
sudo -u www-data php artisan view:cache
sudo -u www-data php artisan config:cache
sudo -u www-data php artisan route:cache
```

Чтобы это не повторялось, обновляйтесь через `sudo bash deploy/update.sh` —
он и права выставляет, и кэш пересобирает.

## Частые задачи

**Посмотреть логи:**

```bash
tail -f /var/www/ict-help/storage/logs/laravel.log   # приложение
tail -f /var/www/ict-help/storage/logs/queue.log     # очередь
journalctl -u ict-help-reverb -f                     # websocket
tail -f /var/log/nginx/ict-help.error.log            # nginx
```

**Перезапустить фоновые сервисы:**

```bash
sudo systemctl restart ict-help-queue ict-help-reverb
```

**Сбросить кэш после правки `.env`:**

```bash
cd /var/www/ict-help
sudo -u www-data php artisan config:cache
```

**Восстановить базу из копии:**

```bash
cd /var/www/ict-help
gunzip < storage/backups/ict_help-20260805-120000.sql.gz | mysql -u ict_help -p ict_help
```

## Настройки установки

Скрипты читают переменные окружения — можно переопределить пути и версии:

```bash
sudo APP_DIR=/opt/ict-help PHP_VERSION=8.4 bash deploy/install.sh
```

| Переменная    | По умолчанию              |
|---------------|---------------------------|
| `APP_DIR`     | `/var/www/ict-help`       |
| `APP_USER`    | `www-data`                |
| `DB_NAME`     | `ict_help`                |
| `DB_USER`     | `ict_help`                |
| `DB_PASSWORD` | генерируется случайно     |
| `PHP_VERSION` | `8.3`                     |
| `SKIP_SEED=1` | пропустить наполнение базы|

## Замечания по безопасности

- `APP_DEBUG=false` и `APP_ENV=production` — уже прописаны в шаблоне `.env`;
  при `APP_DEBUG=true` на боевом сервере тексты ошибок раскрывают структуру
  проекта и параметры подключения.
- Загруженные документы лежат в `storage/app/private` и раздаются только
  через контроллер с проверкой прав — nginx закрывает к ним прямой доступ.
- Файл `.env` ставится с правами `640` и владельцем `www-data`.
- Система рассчитана на внутреннюю сеть колледжа. Если её будет видно из
  интернета — настройте HTTPS (например, `certbot`) и включите
  `SESSION_SECURE_COOKIE=true`.
